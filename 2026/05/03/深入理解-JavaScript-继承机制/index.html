# 深入理解 JavaScript 继承机制：从 ES5 到 ES6 的演进与底层逻辑

在现代前端工程中，开发者大多已习惯使用 ES6 的 class 与 extends 语法来进行面向对象编程。然而，JavaScript 的类与继承在底层依然是基于 原型链（Prototype Chain） 实现的。深入剖析从 ES5 到 ES6 的继承模式演进，不仅有助于编写更健壮的代码，更是深刻理解 JavaScript 语言核心机制的必经之路。

本文将梳理 JavaScript 中主流的继承方案，探讨其实现原理、局限性以及最终的优化路径。

# 现代标准：ES6 的 class 与 extends

ES6 引入了 class 关键字，虽然其本质是原型链的语法糖，但它提供了一种更为清晰、规范的面向对象语法。

# 核心机制剖析：super () 与 this 的生成顺序

在 ES6 的继承机制中， this 的创建过程是 “自顶向下” 的。子类自身并不会立即生成 this 对象，而是必须通过调用 super() （即父类的构造函数），由父类实例化并返回一个 this 引用。子类获取到该引用后，才能在其基础上继续挂载自身的属性（如 this.age = age ）。

如果在子类的 constructor 中未调用 super() 就直接访问 this ，JavaScript 引擎将抛出 ReferenceError 。

# ES5 继承模式的演进史

在 ES6 标准确立之前，开发者通过操控函数与原型链，探索出了多种继承模式。这些模式的演变，本质上是为了解决属性共享与内存冗余之间的矛盾。

# 原型链继承

实现思路： 将子类的原型直接指向父类的一个实例。

  • 优势： 实现了父类原型方法的复用。
  • 局限性：
    1. 引用类型共享问题： 所有子类实例共享父类实例的引用类型属性。若某一个子类实例修改了该属性（例如执行 push ），将导致所有其他实例受影响。
    2. 无法传参： 在实例化子类时，无法向父类的构造函数传递参数。

# 构造函数继承

实现思路： 放弃原型链，在子类的构造函数内部显式调用父类构造函数，从而将属性绑定到当前实例上。

  • 优势： 解决了引用类型数据共享的问题，每个实例都有独立副本；支持向父类传参。
  • 局限性： 无法复用方法。只能继承父类构造函数内部的属性，无法访问父类 prototype 上的方法。且每次实例化都会重新创建函数，造成内存浪费。

# 组合继承

实现思路： 结合前两者的优势，使用 “借用构造函数” 继承实例属性，使用 “原型链” 继承原型方法。

  • 优势： ES5 时期最常用的模式。既支持传参，又保证了引用属性的独立性，同时实现了方法复用。
  • 局限性： 存在性能冗余。父类构造函数被执行了两次，导致子类原型对象（ Child.prototype ）上存在一份多余的父类实例属性。

# 原型式继承

实现思路： 对传入的对象进行浅拷贝。ES5 的 Object.create() 规范化了这一模式。

  • 局限性： 引用类型的属性依然会被所有实例共享。

# 寄生组合式继承（ES5 最佳实践）

实现思路： 为了解决组合继承调用两次构造函数的问题，只需获取父类原型的一个干净副本作为子类原型，而无需实例化完整的父类。

# 深入原理解析：

使用 Object.create(Parent.prototype) 时，如果 Parent.prototype 上存在引用类型，是否仍会引发共享问题？

答案是肯定的。但寄生组合式继承遵循了面向对象的职责划分原则：

  1. 状态（数据 / 属性）由构造函数维护： 易变且需要实例隔离的数据，应始终通过 Parent.call(this) 生成。
  2. 行为（函数 / 方法）由原型维护： 不可变且需要共享的逻辑，挂载在 prototype 上。

通过这种划分，寄生组合式继承实现了属性的隔离与方法的最大化共享，且只调用一次父类构造函数，是现代 ES6 class 编译后的核心实现机制。
